# Release validation

Release truth is split into two evidence classes and neither substitutes for the other.

1. **Hosted matrix evidence** is the GitHub Actions result for the exact source commit. The validation workflow targets Python 3.11–3.13 on Linux, Windows, and macOS.
2. **Packaged validation evidence** is `RELEASE_VALIDATION.json`, regenerated by `scripts/write_validation.py` in the staging environment from commands actually executed there.

The draft-release workflow will not stage an archive unless a successful full hosted validation workflow exists for the exact source SHA. Automatic staging follows a successful validation `workflow_run`; manual staging queries GitHub Actions and rejects a commit without a successful matching validation run. A successful older commit does not satisfy this gate.

The behavioral suite exercises real temporary workspaces: install/update/uninstall, owner-rule preservation, managed-file conflicts, task transitions and concurrency versions, evidence freshness, config/source/log drift, acceptance gates, manual observation labels, review requirements, exact check reuse, failures, time/output bounds, reduced environment, memory provenance/supersession, advisory leases, usage deduplication, event integrity, interruption recovery, and backup restoration.

The complete example exercises the user loop from contract through checks, checkpoint, review, and done. Release checks validate links, distribution contents, Python syntax, profiles, version consistency, release-note/version consistency, and the absence of runtime state. The source archive verifies every manifested byte after writing.

Limitations remain explicit: hosted CI cannot establish every AI-host integration, model behavior, independent reviewer identity, true provider budgets, network isolation, or every external service. The harness does not treat a workflow file, an old green run, or local self-review as current hosted proof.
